## 1. 三种场景总览

| 场景                            | 命令                                                          | 说明                                                                                                                         |
| ------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 整体派生新项目（Monorepo 复用） | `python scripts/new_project.py new my-project`              | 复制整个仓库并重命名项目名 / 仓库名 / 服务分库名 / 版本 / 作者，覆盖 README，删除脚手架专属内容，写入`.scaffold-info.json` |
| 仓库内新增服务                  | `python scripts/new_project.py new-service payment-service` | 从 order-service 模板复制为`services/<name>`，重命名包名 / 服务名 / 表名 / 库名 / 类名前缀                                 |
| 已生成项目升级                  | `python scripts/new_project.py upgrade <project-dir>`       | 三路合并（base 旧版模板 / ours 项目现状 / theirs 新版模板）同步脚手架固有文件，保留业务改动，冲突报告不覆盖                  |

**前置条件**：Python >= 3.10、git。

## 2. 整体派生新项目（new）

### 2.1 方式一：Use this template（推荐）

```bash
# 1) GitHub 上打开脚手架仓库，点击 "Use this template"，填写新仓库名创建（GitHub 生成全新 git 历史）
# 2) clone 新仓库到本地
git clone https://github.com/<org>/<new-repo>.git
cd <new-repo>

# 3) 运行重命名脚本（默认原地重命名，自动删除 scripts/ 自身目录；
#    能力示例模块与组件/实现选择默认交互式逐个询问，可显式 --modules / --components 指定）
python scripts/new_project.py new my-project
python scripts/new_project.py new my-project --modules all                  # 包含全部能力示例模块（免交互）
python scripts/new_project.py new my-project --modules jwt_spi,social_login # 仅包含认证/三方登录示例
python scripts/new_project.py new my-project --modules none --components=cache:redis,mq:rocketmq,payment:wechat

# 4) 按输出提示安装依赖、启动外部依赖、初始化数据库、启动三服务
python -m venv .venv && .venv\Scripts\activate
pip install "flower-web-infrastructure[mysql,redis,nacos,migrate] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git"
pip install -e ".[dev]"
docker compose up -d
cp .env.example .env        # 填写敏感配置
alembic -c services/user-service/alembic.ini upgrade head
alembic -c services/order-service/alembic.ini upgrade head
```

> 说明：`.github/workflows/ci.yml` 中 GHCR 推送地址使用 `github.repository` 自动跟随新仓库，无需修改；首次推送后需在 GitHub `Settings → Packages` 设置三个镜像包可见性。

### 2.2 方式二：手动 clone 脚手架

```bash
git clone https://github.com/flower-star-dream/flower-microservices-scaffolding-py.git my-project
cd my-project
rm -rf .git            # 关键：删除脚手架 git 历史（否则新项目继承脚手架全部提交）
git init               # 新仓库全新历史
python scripts/new_project.py new my-project --git-init
```

## 3. 仓库内新增服务（new-service）

在既有 Monorepo 中新增一个独立业务服务（推荐方式，从 order-service 模板复制）：

```bash
python scripts/new_project.py new-service payment-service
python scripts/new_project.py new-service payment-service --modules none   # 不复制能力示例模块（payment/state_machine）
```

脚本自动完成：

- 复制 `services/order-service` → `services/payment-service`；
- 包目录 `src/order_service` → `src/payment_service`；
- 全局替换：服务名 `order-service` → `payment-service`、包名 `order_service` → `payment_service`、
  表名 `t_order` → `t_payment`、库名 `flower_order` → `flower_payment`、
  类名前缀 `Order*` → `Payment*`、常量前缀 `ORDER_*` → `PAYMENT_*`、
  消息体键 `order_id/order_no` → `payment_id/payment_no`、事件 Topic `order.created` → `payment.created`；
- 文件名同步重命名（`order_controller.py` → `payment_controller.py` 等，与 import 引用保持一致）；
- SQLAlchemy `order_by` 等方法名保留不被误伤。

**生成后必须手工调整**（模板复制自订单域，业务语义需按新域改造）：

1. **端口**：`src/<pkg>/main.py` 的 `SERVICE_PORT` 与 `Dockerfile` `EXPOSE`/`CMD`（默认复制为 8002，请改为空闲端口）；
2. **业务逻辑**：`api / service / mq / schema / constants` 中的接口语义、消息体字段、事件 Topic 按新域调整；
3. **数据库**：`db/init` 新增基线 SQL（`flower_<domain>` 库），或直接编辑本服务 `alembic/versions/` 迁移；
4. **网关路由**：在 `services/gateway/application.yml` 的 `app.gateway.routes` 追加新服务路由（如 `payment: { service: payment-service, prefix: /v1/payments }`）；
5. **CI**：`.github/workflows/ci.yml` 的 `build-image` Job `matrix.service` 追加新服务名；
6. **验证**：`pytest services/<name>/tests` 运行复制后的模板测试，全部通过后再改造业务。

## 4. 项目升级（upgrade）

将已生成项目同步到新版脚手架，采用**三路合并**（diff+patch）：`base`（旧版模板快照）+ `ours`（项目现状）+ `theirs`（新版模板），仅同步脚手架固有文件，**业务改动冲突时报告而不覆盖**。

```bash
# 在脚手架仓库内执行（默认升到当前模板版本；--dry-run 只预览不写盘；
# 能力示例模块默认沿用项目 .scaffold-info.json 的勾选记录，--modules 可覆盖）
python scripts/new_project.py upgrade /path/to/my-project [--to 0.2.0] [--framework-version 0.2.0] [--dry-run]
```

### 4.1 前置条件

- 项目由 `new` 命令生成，且根目录保留了 `.scaffold-info.json`（记录脚手架类型 / 版本 / 替换参数，是升级依据）；
- 脚手架仓库已存在项目对应旧版本的模板快照 `scaffold/versions/v<旧版本>/`（见 [5. 版本发布与快照](#5-版本发布与快照snapshot)）；
- 升级前建议先 `git commit` 当前改动，便于冲突后回溯。

### 4.2 三路合并规则

对每个模板文件，先按项目的替换参数还原为"项目形态"再比较：

| base 旧模板 | ours 项目现状                      | theirs 新模板 | 动作                                         |
| ----------- | ---------------------------------- | ------------- | -------------------------------------------- |
| 不变        | 任意                               | 不变          | 跳过（不触碰）                               |
| 已变        | == base（业务未改）                | 已变          | 更新为新版模板                               |
| 已变        | != base 且 != theirs（业务也改了） | 已变          | **冲突**：报告，不覆盖                 |
| 无此文件    | 无此文件                           | 新增          | 新增补齐                                     |
| 有          | 已删除                             | 有            | 缺失：报告（业务删除了模板文件，需人工确认） |
| 有          | == base                            | 已废弃        | 删除该文件                                   |
| 有          | != base（业务改了）                | 已废弃        | **冲突**：报告，不覆盖                 |

- **README.md** 为业务文件，不参与自动同步（`new` 时已被覆盖），升级后请手工比对；
- **new-service 生成的服务**（如 `services/payment-service`）属于业务代码，不在模板同步范围，不受影响；
- 冲突清单在输出中列出，需手工合并后提交。

### 4.3 框架版本升级

`--framework-version <ver>` 提供时，更新 `.scaffold-info.json` 的 `framework_pin`，并输出框架升级命令（按脚手架 extras 生成，如）：

```bash
pip install "flower-web-infrastructure[min-microservice] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git@v0.2.0"
```

## 5. 版本发布与快照（snapshot）

脚手架每次发布新版本时生成**模板基线快照**，供 upgrade 作为旧版对照（三路合并的 base）：

```bash
# 1) 在脚手架仓库内更新 scripts/new_project.py 的 TEMPLATE_VERSION 为新版本号
# 2) 生成快照（拷贝当前模板，排除脚手架专属内容）
python scripts/new_project.py snapshot 0.2.0
# 3) 提交 scaffold/versions/v0.2.0/ 与脚本变更，可选打 git tag v0.2.0
```

- 快照保存在 `scaffold/versions/v<版本>/`，保留模板原始标识（未替换）；
- `new` 派生新项目时快照目录不复制进业务项目（属于脚手架专属内容）。

## 6. 脚本参数

### 6.1 new（整体派生）

| 参数             | 必填 | 默认                         | 说明                                                                                                                                                                      |
| ---------------- | ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project-name` | 是   | —                           | 新项目名（如`my-project`），用于 pyproject / README / 镜像名 / GHCR 仓库名                                                                                              |
| `--db-name`    | 否   | 项目名转 snake_case          | 服务分库名前缀（如`my-project` → `my_project_user` / `my_project_order`）                                                                                          |
| `--org`        | 否   | `flower-star-dream`        | GitHub 组织名（替换 README 徽章链接；ci.yml 用`github.repository` 自动跟随，无需改）                                                                                    |
| `--version`    | 否   | `0.1.0`                    | 初始版本号                                                                                                                                                                |
| `--author`     | 否   | 不替换                       | 作者（替换`@Author: 花海` 与 pyproject authors）                                                                                                                        |
| `--dir`        | 否   | 当前目录                     | 目标输出目录（提供则复制生成，否则原地重命名）                                                                                                                            |
| `--git-init`   | 否   | false                        | 自动`git init` + 首次提交（手动 clone 方式使用）                                                                                                                        |
| `--modules`    | 否   | 交互式询问（非交互默认 all） | 勾选能力示例模块（`payment,state_machine,jwt_spi,social_login`；`all`=全部 / `none`=不包含；终端下缺省逐个询问，默认不选；CI/脚本非交互环境默认全部，保证开箱即用） |

### 6.2 new-service（新增服务）

| 参数             | 必填 | 默认                         | 说明                                                                                                                                  |
| ---------------- | ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `service-name` | 是   | —                           | 新服务名（如`payment-service`），用于目录 / 包名 / 注册中心服务名                                                                   |
| `--package`    | 否   | 服务名转 snake_case          | Python 包名（`src/<package>`）                                                                                                      |
| `--modules`    | 否   | 交互式询问（非交互默认 all） | 勾选能力示例模块（仅作用于 order-service 宿主模块`payment,state_machine`；`all`/`none`/逗号列表；缺省交互询问，非交互默认全部） |

域名推导：服务名去除 `-service` 后缀作为域名（`payment-service` → `payment`），类名前缀取 PascalCase（`Payment`）、常量前缀取大写（`PAYMENT`）、表名 `t_<domain>`、库名 `flower_<domain>`。

### 6.3 upgrade（升级项目）

| 参数                    | 必填 | 默认                                 | 说明                                                                                                                |
| ----------------------- | ---- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `project-dir`         | 是   | —                                   | 目标业务项目根目录（含`.scaffold-info.json`）                                                                     |
| `--to`                | 否   | 当前模板版本                         | 目标脚手架版本（`x.y.z`）                                                                                         |
| `--framework-version` | 否   | 不更新                               | 目标框架版本（如`0.2.0`），更新 `framework_pin` 并输出升级命令                                                  |
| `--dry-run`           | 否   | false                                | 只预览变更，不写盘                                                                                                  |
| `--modules`           | 否   | 沿用项目`.scaffold-info.json` 勾选 | 覆盖能力示例模块勾选（`all`/`none`/逗号列表；未勾选模块的模板文件不新增、标记块同步移除，保持升级前后模块一致） |
| `--components`        | 否   | 沿用项目`.scaffold-info.json` 记录 | 覆盖组件与实现选择（注册中心强制 Nacos）                                                                            |

### 6.4 snapshot（版本快照）

| 参数        | 必填 | 默认 | 说明                                                          |
| ----------- | ---- | ---- | ------------------------------------------------------------- |
| `version` | 是   | —   | 版本号（`x.y.z`，生成到 `scaffold/versions/v<version>/`） |

### 6.5 组件与实现选择

`new` 支持按框架全部能力组件选择生成：**组件（使用什么）→ 实现（启用哪个实现）→ SPI 策略（默认 / 生产实现 / 自行实现）**。组件清单与单体脚手架一致（见单体脚手架 `docs/创建新项目.md` 5.5 节），微服务形态差异：

- **注册中心强制 Nacos、缓存默认 Redis**：微服务脚手架 `registry` 恒为 `nacos`（服务注册发现必需）、`cache` 默认 `redis`（docker-compose 提供），**禁止内存注册中心**（`--components=registry:memory` 不被接受）；未显式指定时缓存即 Redis，显式 `--components=cache:memory` 可改回内存（本地/测试）；
- **默认最小化**（2026-08-17）：`--components` 只提及显式选择的组件，未提及的可选组件默认 `off`（仅保留必选 `db` 与形态默认 `registry`/`cache`），`all`=全部默认 / `none`=仅必选组件；交互询问回车即取该最小化默认。按需求生成：只勾选用到的组件，`application.yml` 与根 `.env.example` 即按选择裁剪，避免配置全量给出；
- **按服务应用**：各服务 `application.yml` 中该服务使用的组件段按选择替换实现（如 user-service 缓存 `redis`→`memory`、order-service 消息队列 `memory`→`rocketmq`）；未选组件整块移除（回落框架默认）；
- **自研 SPI 骨架按宿主服务生成**：选择策略型实现（`custom` / `orm_custom` 等）的组件生成到对应服务的 `src/<pkg>/spi/`（如 db/cache → user-service、mq/storage/payment → order-service），补全后在该服务装配处接入；数据库组件区分「基于框架 ORM 自定义（`db=orm_custom`）」与「完全自定义（`db=custom`）」两类骨架；
- **根 `.env.example` 联动裁剪**：未选择/关闭组件的环境变量段整块移除；README「启用的组件」表与框架安装 extras 按选择渲染；
- **能力依赖装配（框架 2026-08-17）**：各服务 `application.yml` 的 `app.capabilities.enabled` 由组件选择自动生成（支付 → `"pay"`、JWT/三方登录/安全 → `"authn"` 等），装配时按依赖包含关系自动补足前置（`pay` 自动带上 `authz → authn → user`）；支付为可选能力，不随 `web_infra` 顶层导出，业务代码用 `from web_infra.capabilities.payment import ...` 显式导入（order-service 示例已如此）；
- 选择记录写入 `.scaffold-info.json`，`upgrade` 沿用（`--components` 可覆盖）。

```bash
# 显式指定组件与实现（未指定的取默认；注册中心恒为 nacos）
python scripts/new_project.py new my-project --components=cache:redis,mq:rocketmq,payment:wechat --modules payment,state_machine
```

## 7. 重命名范围

**new（整体派生）**：替换项目名 `flower-microservices-scaffolding` → `<project-name>`、仓库名 `flower-microservices-scaffolding-py` → `<repo-name>`、服务分库名 `flower_user`/`flower_order` → `<db-name>_user`/`<db-name>_order`、版本号、作者；覆盖 README；删除脚手架专属内容（`scripts/`、CLI 测试、设计文档、`*.egg-info` 构建产物）。**保留不动**：框架仓库地址、三个服务的包名/服务名（示例服务保留，业务在此基础上演进）、运行时实例属性（`app.state` / `app.include_router` 等）。

**new-service（新增服务）**：见 [3. 仓库内新增服务](#3-仓库内新增服务new-service)。模板为 order-service（含 Feign 远程调用 / MQ 事件 / 独立库 / 熔断降级等完整微服务形态），生成的包自包含、可独立测试。

## 8. 常见问题

- **改了脚手架代码，但 git 历史仍属于脚手架**：删除 `.git` 后 `git init`（见 2.2 第 3 步），或改用方式一重新生成。
- **要不要把脚手架后续更新同步到新项目**：视情况而定。脚手架新增的**脚手架固有文件**（配置 / CI / Dockerfile / 文档骨架等）可通过 `upgrade` 命令同步（见 [4. 项目升级](#4-项目升级upgrade)）；业务代码请自行演进，模板不会覆盖已改动的文件。
- **upgrade 报"缺少旧版模板基线"**：项目记录的 `scaffold_version` 对应的 `scaffold/versions/v<版本>/` 不存在。原因通常是脚手架仓库未同步到该版本（含快照目录），`git pull` 或切换分支后重试；旧项目若从未生成过快照，需手工升级。
- **生成后测试报 `ModuleNotFoundError: web_infra`**：框架依赖未安装，执行 `pip install "flower-web-infrastructure[min-microservice] @ git+https://github.com/flower-star-dream/flower-web-infrastructure.git"`。
- **new-service 生成的测试报错**：模板测试复制自 order-service，若业务语义已改造需同步修改测试；先跑 `pytest services/<name>/tests` 确认复制无误。
- **CI 推送镜像失败（403 / denied）**：首次推送后在 GitHub `Settings → Packages` 设置新仓库镜像包可见性并授权成员（三服务各一个包）。
